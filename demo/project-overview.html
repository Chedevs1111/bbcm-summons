Project overview

A rebuild of a South African divorce document system that was giving away its clients’ data

Everything the original app did, rebuilt so the browser never touches the database — then extended with Court Online bundles and the operational work a firm actually does around a matter.

Two things nothing here fixes

The original site is still live and still exposed

Browsing bbcmlegal.net with no login and no session renders the full application: eight law firms with real contact details, eleven users, and working “delete firm” controls. It is a client-side app talking straight to a hosted Postgres with the anon key in the public bundle and no row-level gate. The data includes divorce parties, SA ID numbers and payslips.

This rebuild does not touch that site. It needs to be taken down or put behind a login as a separate, more urgent job. No data was created, modified or deleted there during any of this work.

PDF/A conformance is implemented but unvalidated

The bundles carry the required structures — pdfaid:part 2, conformance B, an sRGB OutputIntent, embedded font subsets, a document /ID — and there are tests asserting each one is present and well formed. But no validator (veraPDF) was available in this environment, so nothing has issued a conformance verdict. Run one before advertising PDF/A to a court or a client.

What was built

Three phases
Complete

Phase 1 — Parity and security

Everything the original did: the four-step matter wizard, uploads, Claude vision extraction with per-field confidence, review and override, the template designer, documents and annexures, admin and settings.

Plus the part it had none of — authentication, per-firm authorisation on every route, and an audit trail that is actually written to.

Complete · unvalidated

Phase 2 — Court Online / CaseLines

Paginated, indexed, bookmarked bundles for upload to Court Online. Continuous page numbering, an index citing the page each document actually starts on, and volume splitting per the Gauteng practice directive.

The PDF/A caveat above applies to this phase.

Complete

Phase 3 — Firm operations

Sheriff service tracking, LPC fee notes with the trust/business ledger split, and a client portal that lets a client check status and send documents in without an account.

WhatsApp notifications and ZAR billing were deliberately not built — both need commercial accounts that do not exist yet.

The one change that matters

Architecture

Everything else is detail. In the original, the browser held a database key and queried Postgres directly, so any visitor could ask for anything. Here every read and write goes through a Worker that resolves the session, derives the firm from the user, and scopes the query. There is no path from the browser to the data that skips that step.

Decisions worth knowing

The non-obvious ones

Cross-firm reads return 404, not 403

A 403 tells the caller the record exists and belongs to someone else. Returning 404 means the endpoint cannot be used to enumerate matter ids. Sixty-nine tests assert this on every route, running in the real Workers runtime against real bindings rather than mocks.

Bundles are built with pdf-lib, not HTML-to-PDF

The index has to cite the page each document actually starts on — and the cover sheets and the index are themselves paginated, so adding them shifts the very numbers they list. Rendering HTML would only reveal the pagination after the fact. The page plan iterates to a fixed point before anything is drawn.

Login is rate limited before the password is checked

Password verification runs PBKDF2 at 210 000 iterations, which is the expensive part of the request. Checking the limit afterwards would still refuse an attacker while letting them burn CPU on every attempt. The per-account limit is deliberately looser than the per-IP one, because a tight one would let anyone lock an attorney out of their own files by failing logins against their address.

Money is formatted by hand

toLocaleString('en-ZA') resolves to US formatting inside the Workers runtime but South African formatting in Node and browsers, so the same amount rendered R5,400.00 in a PDF and R6 560,00 in the interface. One explicit formatter is now shared by the server, the PDF engine and the UI.

Gold means brand; amber means caution

The two were the same colour by accident, so a warning carried no more weight than a primary button — “uncontested” sat in alarm-amber on seven of eight template rows. They are now separate scales with separate jobs, documented where the palette is defined.

The client portal exposes surnames and nothing else

The token is 256 bits, stored only as a SHA-256 hash and shown once. Unknown, revoked and expired links all return the same 404. The response is assembled field by field rather than by spreading the matter row, so a column added later cannot leak into it by accident. No ID numbers, addresses, income, pleadings or fee notes appear.

Bugs the tests did not catch

Found by running it

Each of these passed a green test suite. They were found by opening the app and looking at the output — which is why the walkthrough is part of the process and not a formality.

What was wrongWhy it was invisible
Malformed PDF/A metadata. The em dash in a bundle title was written as byte 0x14, a control character illegal anywhere in XML, leaving the metadata packet unparseable. Every existing test decoded the PDF as latin-1, which round-trips any byte at all. An encoding fault could not be seen. The new tests read raw bytes.
Centred headings were only half centred. (GAUTENG DIVISION, PRETORIA) sat at the left margin in every pleading, because the centre marker did not carry across a line break. Assertions checked the markers parsed, not where the text landed.
Bookmarks read Annexure ˝D˛. Outline titles were encoded in PDFDocEncoding instead of UTF-16. The bookmark existed and had a title, which is all the test asked.
Bundle text extracted one word per line, so phrase search in CaseLines could never match. The text was present and correct; only its run structure was wrong. Coalescing runs also cut file size 18%.
A seed script wrote the literal string “undefined” as the body of two court templates. A regex missed one constant name. The script now throws rather than writing a placeholder.
Login had no brute-force protection at all, over a 210 000-iteration hash. Nothing tested for the absence of a limit. Found by re-reading delivered work rather than by a failure.

Not proven

PDF/A conformance has no validator verdict. The Claude extraction path has never run against a real document — it needs an API key and scanned samples, and the confidence threshold that decides what gets flagged for review is currently a guess. Seven screens were reconstructed from the original’s JavaScript bundle rather than copied, because creating a matter in the live shared database to see them was not acceptable; they work, but their layout is a design decision and deserves a look from someone who used the original daily.
